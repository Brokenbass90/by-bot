# signal_copy — оценка и план

Полуавтоматическое копирование сигналов из закрытого Telegram-канала в MetaTrader 5,
отдельным модулем внутри `bybit-bot-clean-v28`, с приоритетом «сначала статистика, потом торговля».

Дата: 19 августа 2026. Основано на чтении реального кода проекта, не на предположениях.

---

## 0. Короткий ответ

**Реализуемо.** Причём дешевле, чем кажется: примерно 40% нужного уже написано в твоём проекте
и лежит без дела. Три вещи, которые меняют картину против первоначального плана:

1. **`MetaTrader5` (pip) — только Windows.** Все девять wheel-файлов последней версии 5.0.6090
   (1 августа 2026) помечены `win_amd64`, macOS-сборки нет и не планируется. На Mac терминал
   работает через Wine-обёртку, и Python-коннектор туда достаётся только через Windows-Python
   *внутри* Wine-префикса. Это костыль, который ломается при каждом обновлении терминала.
   Ты сказал: «надо чтобы торговля шла там, какой ноут не спит, для обеих систем» —
   **значит Python-пакет не подходит вообще.** Нужен MQL5-советник как исполнитель.
   Он живёт внутри терминала и на Mac, и на Windows работает одинаково.

2. **Советник вместо Python-пакета — это не компромисс, а лучшая архитектура для твоих же
   требований.** Ты потребовал: «ИИ никогда не имеет доступа к отправке ордера» и «торговый
   пароль не хранить в приложении». Советник даёт и то, и другое бесплатно: терминал уже
   залогинен, пароль нигде не появляется; а направление связи разворачивается — не наш код
   зовёт `order_send`, а советник опрашивает нашу очередь и забирает оттуда только команды
   со статусом `APPROVED`. Питон физически не имеет функции отправки ордера. Это не политика
   доступа, это отсутствие кода.

3. **Два ноутбука с одним счётом — главный технический риск проекта, важнее парсера.**
   Два терминала, залогиненных в один счёт, оба с советником, оба опрашивают очередь → двойное
   исполнение. Лечится лизом (лидер-лизом) и идемпотентным ключом на команду. Расписано в §7.

Дальше — по твоим тринадцати вопросам, потом план.

### Найденный баг в коде, который будем переносить

`scripts/forex_mt5_demo_bridge.py:261`:

```python
filling_mode = getattr(info, "filling_mode", mt5.ORDER_FILLING_IOC)
request = {..., "type_filling": filling_mode}
```

`symbol_info.filling_mode` — это **битовая маска разрешённых режимов**
(`SYMBOL_FILLING_FOK=1`, `SYMBOL_FILLING_IOC=2`), а `type_filling` ждёт **конкретный режим**
из другого перечисления (`ORDER_FILLING_FOK=0`, `ORDER_FILLING_IOC=1`, `ORDER_FILLING_RETURN=2`).
Значения не совпадают. У брокера, который разрешает только FOK, маска = 1, и код пошлёт
`type_filling=1` = IOC → отказ `Unsupported filling mode`. У нас это будет:
проверить бит, выбрать поддерживаемый режим, и если ни один не подходит — отказ до отправки.

## 2. Где держать код и как его потом выключить

Ты просил: отдельная директория, чтобы отключить и ничего не сломалось. Делаем сильную версию
этого требования — **отдельный процесс**, а не только отдельная папка.

```
bybit-bot-clean-v28/
└── signal_copy/                  ← вся новая жизнь здесь
    ├── README.md
    ├── requirements.txt          ← свои зависимости (telethon, pydantic)
    ├── config.example.env
    ├── app.py                    ← свой FastAPI, свой порт 8766
    ├── db/
    │   ├── schema.sql
    │   └── store.py              ← своя SQLite: signal_copy/data/signal_copy.db
    ├── parse/                    ← normalize · symbols · rules · llm · schema · confidence
    ├── resolve/linker.py         ← сообщение → группа сделки
    ├── risk/                     ← sizing · limits · kill_switch
    ├── execution/
    │   ├── contract.py           ← интерфейс исполнителя
    │   ├── ea_queue.py           ← очередь команд для советника
    │   └── mt5_python.py         ← опциональный Windows-адаптер
    ├── stats/                    ← replay · metrics · report
    ├── telegram/                 ← bot_api (Шаг 1) · mtproto (Шаг 2)
    ├── ea/SignalCopyBridge.mq5   ← советник, ставится в оба терминала
    ├── web/                      ← роуты и одна страница
    └── tests/
```

Правила изоляции, которые делают выключение бесплатным:

- **Импорты только в одну сторону.** `signal_copy` может импортировать `bot.*` и `web.auth`.
  Ни один файл вне `signal_copy/` не импортирует `signal_copy`. Проверяется тестом
  (`tests/test_isolation.py` грепает дерево) — не соглашением, а красной сборкой.
- **Своя база.** Отдельный `.db`-файл. Не таблицы в `trades.db`, чтобы удаление было `rm -rf`.
- **Свой процесс и свой systemd-юнит.** Выключение = `systemctl stop signal-copy`.
  Основной бот об этом не узнаёт.
- **Точек касания существующего кода: ноль.** Опционально — один блок в `web/main.py`
  под `try/except` и флагом `SIGNAL_COPY_ENABLE`, если захочешь единый порт. Не рекомендую
  на первом этапе: отдельный порт даёт настоящий рубильник.
- **Свои переменные окружения** с префиксом `SIGCOPY_`, свой файл `signal_copy/.env`.

Полное удаление: `rm -rf signal_copy/` + снять юнит. Всё.

## 3. Как связать с MetaTrader 5 (вопросы 3, 4, 5, 6)

### Решение: советник в терминале, а не Python-пакет

```
   Mac (спит/не спит)              Windows (спит/не спит)
   ┌──────────────┐                ┌──────────────┐
   │ MT5 terminal │                │ MT5 terminal │
   │ + советник   │                │ + советник   │
   └──────┬───────┘                └──────┬───────┘
          │  HTTPS (WebRequest, раз в 2 сек)│
          │  pull APPROVED / push snapshot  │
          └───────────────┬─────────────────┘
                          ▼
          ┌────────────────────────────────┐
          │  signal_copy на всегда-живом    │
          │  сервере (там же, где bybot)    │
          │  очередь · база · веб · парсер  │
          └────────────────────────────────┘
```

**Почему сервер, а не Mac.** Если координатор живёт на маке, а мак заснул — второй терминал
опрашивает мёртвый адрес. У тебя уже есть всегда-живой сервер с `bybot.service`. Туда же
ставим `signal_copy`. Ноутбуки становятся сменными руками, а голова одна и не спит.

**Что советник умеет** (весь твой список функций, всё это есть в MQL5):

| Твоё требование | MQL5 |
|---|---|
| подключение к залогиненному терминалу | не нужно — советник *внутри* него |
| текущий счёт, balance/equity/free margin | `AccountInfoDouble/Integer` |
| symbol info, Bid/Ask, spread, contract size, tick size/value | `SymbolInfoDouble/Integer` |
| доступность инструмента | `SymbolInfoInteger(SYMBOL_TRADE_MODE)`, `SymbolSelect` |
| расчёт лота от риска | `OrderCalcProfit` — см. §8 |
| `order_check()` | `OrderCheck` |
| `order_send()` | `OrderSend` |
| SL/TP при открытии и изменение | `TRADE_ACTION_DEAL` / `TRADE_ACTION_SLTP` |
| ticket/order/deal id | `MqlTradeResult.order`, `.deal`, `PositionGetInteger(POSITION_TICKET)` |
| открытые позиции | `PositionsTotal` / `PositionGetTicket` |
| история сделок | `HistorySelect` + `HistoryDealGet*` |
| закрытие и частичное закрытие | `TRADE_ACTION_DEAL` встречным объёмом |

**Настройка на обеих системах одинаковая:** положить `.mq5` в `MQL5/Experts`, скомпилировать,
повесить на любой график, в `Сервис → Настройки → Советники` разрешить WebRequest для нашего
URL. Один и тот же файл, один и тот же чек-лист на Mac и на Windows.

### Ограничения, которые надо знать заранее (вопрос 4)

- **`WebRequest` синхронный и блокирует поток.** Звать только из `OnTimer` с таймаутом
  1500 мс, никогда из `OnTick`. Иначе терминал начнёт лагать.
- **`WebRequest` не работает в тестере стратегий.** Нам не нужно, но знать стоит.
- **Один поток на все советники в терминале.** Держим один экземпляр советника на терминал,
  а не по одному на символ.
- **URL нужно внести в белый список руками.** Автоматизировать нельзя — это защита MetaQuotes.
  Разовая настройка, попадает в чек-лист установки.
- **JSON в MQL5 придётся парсить самому** — стандартной библиотеки нет. Поэтому протокол
  делаем плоским: одна команда = одна строка с разделителями, не вложенный JSON.
  Ответы советника — тоже плоские. Меньше кода в самом хрупком месте.
- **Демо-счёт брокера может отключаться по выходным** и на нерыночных инструментах.
  Советник обязан отличать «нет связи» от «рынок закрыт» и говорить это в снимке.

### Опциональный второй адаптер

`execution/mt5_python.py` на Windows через pip-пакет — оставляем как *второй* исполнитель
за тем же интерфейсом `ExecutionAdapter`. Полезен для отладки и для быстрых read-only
экспериментов на винде. Но контур, который торгует, — один, и это советник.
Два живых исполнителя одновременно запрещены на уровне лиза (§7).

## 4. Парсер: гибрид, и LLM в строго очерченной клетке (вопрос 7)

Только LLM — плохо. Только regex — не покроет «докупился‼️» и свободные апдейты.
Гибрид, но не «regex, а если не вышло — спросим модель», а вот так:

**Слой 1. Детерминированный.** Словарь символов и алиасов (`GOLD`→`XAUUSD`, `ЗОЛОТО`→`XAUUSD`),
ключевые слова стороны (`BUY/SELL/лонг/шорт/buy limit`), извлечение чисел с ролью
(`SL`, `TP`, `TP2`, вход, диапазон). Твой формат `GOLD BUY 4390-4393 / SL 4380 / TP 4410 / TP2 4425`
покрывается правилами на 100%, без единого обращения к модели. Это большинство сообщений.

**Слой 2. LLM — только когда слой 1 не закрыл обязательные поля,** и только на свободном тексте.
Вызов через уже готовый `ai_routes` плумбинг (DeepSeek дёшев).

**Здесь ключевая защита, ради которой всё затевалось:**

> Каждое число в ответе модели обязано присутствовать в исходном тексте дословно.
> Проверка — обычное вхождение подстроки, после нормализации разделителей.
> Не нашли — поле отбрасывается, сигнал уходит человеку.

Это убивает галлюцинацию цены как класс. Модель физически не может выдумать стоп 4380,
если в сообщении его нет. Она может только *выбрать* из того, что написано, и *назвать роль*.
Раскладывание чисел по ролям — задача, где модель сильна; изобретение чисел — то, где
она опасна. Мы разрешаем первое и делаем невозможным второе.

**Слой 3. Схема и семантика.** Pydantic-модель + проверки, которые важнее схемы:

- BUY ⇒ `SL < entry < TP1`; SELL ⇒ зеркально. Нарушение — жёсткий отказ, не предупреждение.
- Стоп обязателен. Нет стопа — исполнение запрещено (твоё требование, реализуется здесь).
- `|entry − SL|` больше брокерского `SYMBOL_TRADE_STOPS_LEVEL`. Иначе сервер откажет,
  и лучше узнать это до превью, а не после.
- Символ существует в списке терминала, с учётом суффиксов брокера (§10, риск 3).
- Расстояния до SL/TP в разумных процентах от цены — защита от опечатки на порядок
  (`SL 438` вместо `4380`).

**Confidence считаем сами, не спрашиваем у модели.** Само-оценка LLM некалибрована и коррелирует
с уверенностью формулировки, а не с правотой. Наша `confidence` — доля обязательных полей,
закрытых слоем 1, со штрафом за каждое поле, пришедшее только от модели, и за каждую
сработавшую эвристику. Число прозрачное и воспроизводимое: по логу видно, из чего оно сложилось.

**Порог.** Ниже порога — исполнение блокируется, показывается человеку с пометкой, чего не хватило.
Никогда не «выполнить с оговоркой».

## 5. Как связывать сообщения в одну сделку (вопрос 9)

Модель данных — три таблицы вместо одной.

**`signal_group`** — сделка как замысел: `group_id`, символ, сторона, вход, SL, список TP,
статус (`NEW / APPROVED / OPEN / PARTIAL / CLOSED / SKIPPED / EXPIRED`), `channel_id`,
время первого сообщения, канальный источник.

**`signal_message`** — каждое сообщение: `message_id`, `group_id` (может быть NULL до привязки),
`raw_text`, `edit_date`, `content_hash`, результат парсера, `confidence`,
**`link_reason`** — как именно привязали.

**`execution`** — каждое действие у брокера: `client_order_id`, тикет, объём, цена, время,
запрос и ответ терминала целиком.

**Порядок разрешения привязки, от надёжного к гадательному:**

1. `reply_to_message_id` — если в канале ответили на исходное сообщение. Это точная связь,
   и она бесплатно появляется на Шаге 2 через MTProto. Ради одного этого поля стоит
   дойти до MTProto.
2. В апдейте назван символ, и по нему открыта ровно одна группа → привязка.
3. Символ не назван, но открыта ровно одна группа вообще → привязка с пометкой
   `link_reason='sole_open_group'`.
4. Кандидатов больше одного → **не гадаем**. Показываем человеку:
   «Предположительно речь о текущей XAUUSD BUY. Что сделать?» с выбором.

Плюс окно давности: апдейт не привязывается к группе старше N часов, если группа уже закрыта.

**Правило, которое стоит зафиксировать сразу:** если `link_reason` — эвристика (3 или 4),
автоисполнение запрещено навсегда, на всех этапах, включая полностью автоматический режим,
если ты когда-нибудь до него дойдёшь. Привязка по догадке и деньги не встречаются.

## 6. Расчёт лота для XAUUSD, индексов и крипто-CFD (вопрос 8)

Форекс-формула (`риск / (пипсы × стоимость пипса)`) на золоте и индексах врёт. Правильный ответ
уже реализован в твоём же `_estimate_volume_mt5` — спросить у брокера:

```
loss_per_lot = |OrderCalcProfit(тип, символ, 1.0 лот, цена_входа, цена_стопа)|
risk_cash    = equity × risk_pct
raw_lot      = risk_cash / loss_per_lot
lot          = округлить(raw_lot) по volume_step, зажать в [volume_min, volume_max]
```

Красота в том, что `OrderCalcProfit` — функция самого терминала. Она уже знает `contract_size`,
`tick_value`, валюту котировки, валюту счёта и текущий кросс-курс. Одна формула на EURUSD,
XAUUSD, US500 и BTCUSD — потому что формулы нет, есть вопрос брокеру.

Проверка на твоём примере: XAUUSD, вход 4390, стоп 4380, контракт 100 унций.
`loss_per_lot = 10 × 100 = $1000`. При депозите $4000 и риске 0.5% = $20 → `raw_lot = 0.02`.
Совпадает с превью, которое ты набросал.

**Обязательные проверки после расчёта:**

- `raw_lot < volume_min` → не «округлить вверх до 0.01», а **отказ**: риск на минимальном
  лоте превысит заданный. Показать человеку, во сколько раз. Это частый случай на золоте
  с маленьким депозитом, и молчаливое округление вверх — как раз то, что убивает счета.
- `lot > SIGCOPY_MAX_LOT` → зажать и пометить `binding_constraint='max_lot'`.
- Проверка свободной маржи через `OrderCheck` до отправки, а не после отказа.
- `fill_fraction` — если пришлось зажать лот, показать, какая доля желаемого риска реально берётся.
  Форма ответа — из `RiskSizeDecision`, чтобы читалось как остальной проект.

**Глобальные рельсы поверх сигнала** (твой список, в порядке проверки): kill switch →
demo/live гейт → дневной лимит убытка → максимум одновременных сделок → суммарный риск
открытых позиций → спред ≤ порога → стоп присутствует → лот считается → маржа хватает.
Первый отказ останавливает цепочку и пишется в лог с причиной.

## 7. Дедуп и защита от двойного исполнения (вопрос 10)

Три независимых уровня — потому что цена ошибки здесь максимальная, а два ноутбука
делают ошибку вероятной.

**Уровень 1. Дедуп сообщений.** Уникальный индекс `(channel_id, message_id)`.
Плюс `content_hash = sha256(нормализованный текст)` — ловит пересланное или скопированное
второй раз сообщение. Правки в Telegram не создают новое сообщение: храним `edit_date`
и версию, правка — новая версия, а не новый сигнал.

**Уровень 2. Идемпотентность команды.** В момент подтверждения генерируется `client_order_id`.
Он уходит в терминал как `magic` + `comment`. Советник **до отправки** проверяет позиции
и историю на этот идентификатор; нашёл — не отправляет, а рапортует «уже исполнено».
Повторный клик по кнопке, ретрай сети, перезапуск советника — всё безопасно.

**Уровень 3. Лиз на исполнителя — то, ради чего этот раздел.**
При двух терминалах на одном счёте:

- Каждый советник представляется `terminal_id` (уникальный, генерируется при установке).
- Сервер держит **лиз**: имя текущего активного терминала и срок годности (например 15 секунд).
- Команду `APPROVED` забирает только держатель лиза. Забор — атомарный
  `UPDATE ... WHERE status='APPROVED' AND claimed_by IS NULL`, одна строка, один победитель.
- Терминал без лиза продлевает *заявку* и получает команды только после того, как лиз держателя
  протух (ноутбук заснул) — тогда лиз переходит.
- В UI видно, чей сейчас лиз. Ты в любой момент видишь, какой ноут «руки».

Без лиза два терминала откроют две позиции по одному сигналу, и заметишь ты это уже по факту.
Идемпотентный ключ помогает, но лиз — первичная защита, ключ — вторичная.

## 8. Demo / Live (вопрос 11)

**Тип счёта берётся из терминала, не из нашего конфига.** `AccountInfoInteger(ACCOUNT_TRADE_MODE)`
возвращает DEMO / CONTEST / REAL. Логика:

- Конфиг говорит demo, терминал говорит real → **жёсткий отказ**, громкий алерт, ничего не шлём.
  Это защита от «подключил не тот терминал» — самая вероятная бытовая ошибка.
- Каждая запись в базе несёт `account_login` + `trade_mode` + `broker_server`.
  Статистика демо и live **никогда** не складывается в один отчёт, на уровне запроса.
- Live требует отдельного включения (`SIGCOPY_ALLOW_LIVE=1`), плюс второе подтверждение
  с вводом суммы риска прописью, плюс живой токен сессии по образцу `bot/ai_manual_trade.py`.
- Смена счёта в терминале — событие, а не мелочь: советник рапортует логин в каждом снимке,
  сервер сверяет с ожидаемым и при расхождении отзывает лиз.

## 9. Статистика: что считаем и что 50 сигналов реально докажут

Пишем по сигналу всё из твоего списка: время публикации, цена на момент получения, цена
фактического исполнения, задержка, спред, проскальзывание, риск, лот, TP/SL, итоговый PnL,
результат в R, максимальное движение в плюс (MFE) и против (MAE), были ли докупки,
число модификаций, был ли сигнал пропущен.

Считаем: винрейт, средний плюс, средний минус, средний R, ожидание, profit factor,
максимальная просадка, суммарный PnL, разрезы по инструменту, по стороне, по времени суток.

**Главное число, которое ты назвал: разница между заявленным каналом и полученным тобой.**
Оно раскладывается на три слагаемых, и каждое надо мерить отдельно, иначе цифра
неинтерпретируема:

1. **Разметка исхода.** Канал говорит «TP взят». Мы проверяем по свечам: что случилось раньше,
   TP или SL. Это чистое расхождение фактов, самое ценное.
2. **Задержка.** Разница между ценой в момент публикации и ценой, по которой вошёл бы ты.
   Ровно то, что съедает подписчика.
3. **Издержки.** Спред, комиссия, своп за ночь. На золоте своп заметен.

**Про размер выборки — честно, потому что ты сам требуешь считать различимость до прогона.**
При разбросе одной сделки около 1R:

- **50 сигналов хватит**, чтобы поймать враньё про винрейт. Если канал заявляет 80%, а реально
  55% — при n=50 стандартная ошибка доли ≈ 7 пп, разрыв в 25 пп читается как ~3.5σ.
  Диагноз ставится уверенно.
- **50 сигналов не хватит**, чтобы доказать эдж. Различимое среднее R при n=50 — это ±0.28R.
  Чтобы отличить +0.1R от нуля, нужно около 380 сделок; чтобы отличить +0.2R — около 100.

Поэтому цель Шага 0 формулируется так: **не «есть ли у канала эдж», а «говорит ли канал правду
о своих же результатах».** На это 50 сигналов ответят. И, судя по тому, как обычно устроены
платные каналы, ответ на второй вопрос станет очевиден раньше, чем наберётся статистика на первый.

## 10. Риски и проблемы, которые видно заранее (вопрос 12)

**Технические**

1. **Двойное исполнение с двух ноутбуков** — главный. Лечится лизом (§7). Не откладывать.
2. **Ноутбук заснул с открытой позицией.** Стоп физически стоит у брокера, так что катастрофы
   нет. Но команды сопровождения («в безубыток») молча копятся в очереди. Нужен TTL на команду
   и алерт «команда протухла, не исполнена».
3. **Имена символов у брокера.** `XAUUSD` может называться `GOLD`, `XAUUSD.r`, `XAUUSDm`,
   `XAUUSD.pro`. Строим карту из **фактического списка символов терминала**, а не из константы
   в коде. Неотображённый символ — отказ, не догадка.
4. **`SYMBOL_TRADE_STOPS_LEVEL` и `FREEZE_LEVEL`.** Брокер не примет стоп ближе N пунктов.
   Проверять до превью.
5. **Режим заполнения (filling mode)** — описанный в §1 баг. Прочитать маску, выбрать
   поддерживаемый режим, при отсутствии — отказ.
6. **Интерпретация диапазона входа `4390-4393`.** Это «по рынку сейчас» или «лимитник по
   лучшему краю»? Это не техническая мелочь, а решение, которое **материально меняет
   статистику**. Зафиксировать политику в конфиге, писать её в каждую запись и на Шаге 0
   считать оба варианта — они сравнимы бесплатно, пока ордеров нет.
7. **Часовые пояса.** Время сообщения, время сервера брокера (обычно UTC+2/+3), твоё время.
   Всё хранить в UTC, показывать в локальном. Разрез «по времени суток» иначе бессмысленный.
8. **Выходные и гэпы.** Золото и индексы открываются с разрывом. Реплей должен помечать
   исходы, случившиеся через гэп, отдельно — иначе они выглядят как исполнение по цене,
   которой не было.

**Со стороны канала**

9. **Удаление и правка сообщений.** Каналы редактируют историю, в том числе задним числом.
   На Шаге 2 логировать события удаления и правки. Это, возможно, самая интересная строчка
   в будущем отчёте.
10. **Неполные сигналы.** Часть каналов сознательно публикует вход без стопа, а стоп «в личку».
    Такие сигналы у нас автоматически неисполнимы — и это правильно, но надо понимать,
    какая доля потока отвалится.

**Прочее**

11. **Автоматическое чтение платного закрытого канала** может нарушать его правила,
    а userbot на MTProto Telegram иногда трактует как автоматизацию аккаунта. Риск не
    технический, но реальный: аккаунт. Поэтому Шаг 2 — только чтение одного разрешённого
    `channel_id`, без реакций, без пересылок, без ответов, с человеческим темпом.
12. **Сессия Telethon — это полный доступ к твоему аккаунту.** Файл сессии шифровать,
    класть вне репозитория, права 600, в `.gitignore` до того, как он появится.
13. **Тексты канала уходят к LLM-провайдеру.** Технически нормально, но знать стоит;
    при желании слой 2 отключается флагом, тогда работает только regex.

## 11. Пошаговый план

Оценки — в человеко-днях сфокусированной работы, не в календаре.

### Шаг 0 — статистика без MT5 и без ордеров (~4-5 дней)

Ровно то, что ты потребовал: вставляю сообщение → парсер → запись с ценой на момент
публикации → сам подтягивает котировки и считает, что было бы.

| # | Что | Готово, когда |
|---|---|---|
| 0.1 | Скелет `signal_copy/`, своя SQLite, свой сервис на 8766, `require_auth` из веба | `/ping` отвечает, тест изоляции зелёный |
| 0.2 | Слой 1 парсера + карта символов + семантические проверки | 20 твоих реальных сообщений разбираются, разбор в тестах |
| 0.3 | Страница «вставить сообщение» → разбор → сохранение группы | Ни строчки кода, умеющей слать ордер, в проекте нет |
| 0.4 | Снимок цены в момент сохранения + фиксация задержки | В записи есть `price_at_publish`, `price_at_capture`, `capture_latency_sec` |
| 0.5 | Слой 2 (LLM) с проверкой «число обязано быть в тексте» | Тест: подложить модели выдуманную цену → поле отброшено |
| 0.6 | Движок реплея: по минуткам решить, что было раньше — SL или TP; посчитать R, MAE, MFE | Прогон по накопленным сигналам воспроизводим |
| 0.7 | Метрики и страница отчёта | Винрейт, средний R, ожидание, PF, просадка + разрезы |
| 0.8 | **Отчёт «заявлено vs получил бы»**, разложенный на разметку / задержку / издержки | Это выход Шага 0 |

**Источник котировок.** Ты не ответил на этот вопрос, беру решение сам и говорю прямо:
начинаем с `scripts/fetch_forex_dukascopy.py`, который уже в проекте — бесплатно, минутки,
есть XAUUSD и мажоры; для BTC берём публичный Bybit, он у тебя и так подключён.
Этого достаточно, чтобы Шаг 0 стартовал сегодня и не зависел от MT5. Как только на Шаге 1
появится советник, он начнёт присылать цены **твоего брокера**, и весь реплей пересчитывается
на них — это правильнее, потому что исполняться ты будешь по ним же. Расхождение двух прогонов
само по себе полезное измерение.

**Критерий выхода:** 50 сигналов, отчёт построен, три слагаемых расхождения посчитаны.
Только после этого — Шаг 1.

### Шаг 0.5 — советник в режиме чтения (~2 дня, можно параллельно)

Ставим `SignalCopyBridge.mq5` в оба терминала **без права торговли**. Он только шлёт снимок:
счёт, тип счёта, символы, спецификации, тик, спред, открытые позиции. Это даёт:
живое превью лота на настоящих данных брокера, проверку карты символов, обкатку `WebRequest`
и лиза — всё это до того, как появится хоть один ордер. Дешёвый способ снять половину
рисков Шага 1 заранее.

### Шаг 1 — demo, полуавтомат копипастой (~5-6 дней)

| # | Что |
|---|---|
| 1.1 | Протокол команд + лиз + идемпотентный `client_order_id` |
| 1.2 | Расчёт лота через `OrderCalcProfit` + `OrderCheck` до отправки |
| 1.3 | Экран превью: символ, сторона, вход, SL, TP, баланс, риск в деньгах, лот, связывающее ограничение. Кнопки `OPEN TRADE` / `EDIT` / `SKIP` |
| 1.4 | Одноразовый токен подтверждения (по образцу `bot/ai_manual_trade.py`) |
| 1.5 | Отправка → проверка исполнения → сверка позиции → запись `execution` |
| 1.6 | Рельсы: kill switch, дневной лимит, максимум сделок, суммарный риск, максимальный спред, запрет без стопа |
| 1.7 | Полный аудит-лог: исходный текст → разбор → правки человека → расчёт → запрос → ответ терминала → исполнение |

**Критерий выхода:** 20+ demo-сделок, ни одного двойного исполнения при двух включённых
терминалах (проверить намеренно), измеренное проскальзывание, полный лог по каждой.

### Шаг 2 — чтение канала через MTProto (~3 дня)

Telethon, только чтение, только разрешённые `channel_id`, сессия вне репозитория.
Новые сообщения идут в тот же парсер. Режим прежний: `NEW SIGNAL → parsed → confirmation → execute`.
Бонус, ради которого стоит идти: `reply_to_message_id` — точная привязка апдейтов вместо эвристик.
Плюс логирование правок и удалений.

### Шаг 3 — сопровождение позиций (~4 дня)

`докупился`, `в безубыток`, `закрыл половину`, `перенёс стоп`, `TP1 взят`, `закрываем всё`.
Каждое — команда с обязательным подтверждением. Для каждой:
пересчёт общего риска после действия и явный показ нового риска до подтверждения.
«Докупился» без указанного объёма — всегда вопрос человеку, никогда догадка.

### Чего в плане намеренно нет

Полного автоисполнения. Он появится в разговоре сам, когда демо-статистика будет
выглядеть хорошо. Ответ на него — цифры Шага 0: если разрыв между заявленным и полученным
велик, автоисполнение просто масштабирует чужую ошибку.
