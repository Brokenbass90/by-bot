## Почему это происходит

`5b4a272:ten_pump4.py:168–182` создаёт новый `K()` для каждого символа/прохода.
Проверки `ts < nachalo` и `key in vidennye` стоят **до** `maybe_signal`.
Таким образом, виденная сигнальная свеча исчезает и из ценовых буферов, и из
переходов состояния производителя. На следующем проходе она уже не выставляет
cooldown. Непрерывный пересчёт `pump4_pereschet.py:142–158` таких пропусков
не делает. В стратегии буферы обновляются на строках 1036–1041, подавление
cooldown — 1045–1048, установка cooldown после сигнала — 476.
Длинный прогрев другой последовательности вызовов эту разницу не устраняет.

Вторая проблема трассировки: тень/пересчёт выставляют `PUMP4_*`, а производитель
читает `PF_*`. По журналу нельзя восстановить фактическое унаследованное
окружение каждого старого процесса. Совпадение сегодняшних файлов с Git не
подтверждает содержимое уже загруженного исторического интерпретатора.

## Граница доказательства и следующий шаг

Снимки свечей ретроспективные. `zapisano` задаёт приближение окна latest1000,
предыдущие строки журнала — приближение исторического `vidennye`; настоящий
pass-start state и точный момент запроса отсутствуют. Не записаны исходные
ответы API, PF-конфигурация, загруженная версия кода, границы проходов,
исключения и полная геометрия исходных сигналов. Поэтому историческая причина
каждого процесса остаётся `NOT_ATTESTED`, хотя механизм достаточен для всех51.
Полное совпадение геометрии с исходным журналом также недоказуемо: её там нет.

34 `SDVIG_CHASA` оставлены отдельной группой. Сигналы не переносились к соседним
часам и не добавлялись в 51. Диагностика Claude использует смещения строк,
не проверенный по непрерывным свечам перевод timestamp; её метка сама по себе
не доказывает ошибку часов.

Не следует ни добавлять 51 в торговлю, ни удалять их из статистики и объявлять
старую экономику исправленной. Для research-владельца подготовлено конкретное
исправление обёртки: передавать каждую закрытую свечу в непрерывный frozen
производитель ровно один раз, а фильтровать только публикацию; сохранять
input/config/code/state/decision hashes и границы эпох. Сначала доказать parity
с существующим intake, затем накапливать корректный forward. Изменения тени и
новые оценки доходности в этом цикле не запускались.
