# Ускорение ресёрча: Mac как research-хост + распараллеливание (2026-07-01)

Вопрос владельца: можно нагрузить Mac, чтобы быстрее получить данные? ДА — и это правильно.

## Разделение ролей (жёстко)
- **1GB live-VPS**: ТОЛЬКО live-бот + liquidation/funding/OI коллектор (пишет данные вперёд).
  Никаких тяжёлых свипов рядом (уже дважды ловили runaway -> OOM).
- **Mac (research-хост)**: ВСЕ тяжёлые бэктесты/WF/свипы. Многоядерный, RAM много -> быстрее в разы.

## Распараллеливание на Mac (Codex)
1. **Сбор данных параллельно**: тянуть funding/OI/liq историю по символам конкурентно
   (пул из N воркеров, N=число ядер-1). Символы независимы -> линейное ускорение.
2. **WF-свипы шардить по символам/параметрам**: запускать несколько `screen`/процессов,
   каждый на своём подмножестве (SOL | AVAX | LINK | MATIC параллельно, не последовательно).
3. **caffeinate**: `caffeinate -dimsu <cmd>` — чтобы Mac не уснул и не убил прогон
   (сейчас риск: "если Mac не уснёт"). Обязательно оборачивать длинные ресёрчи.
4. Результаты -> в общий репозиторий/reports, Claude разбирает по OOS.

## Что это даёт
H4-данные (funding/OI/liq по 4 mid-caps) и WF нескольких кандидатов — параллельно за
часы вместо последовательных суток. Live не трогаем, VPS только собирает и торгует ATT1.

## Практика
- Codex: обернуть текущий и будущие sweep-скрипты в `caffeinate` + шардинг по символам.
- Пул сбора данных: 1 процесс на символ, писать в data_cache/{funding,oi,liq}/.
- Claude (локально, лёгкое): готовить конфиги шардов + разбор результатов; тяжёлое — Mac.
